# Migration Plan: Supabase (Postgres) → Azure SQL Database

## Why / Scope

Today `WorkoutManager.Data` and every repository in `WorkoutManager.BusinessLogic` are built
directly on the `Supabase`/`Supabase.Postgrest` client library — table models use Postgrest
attributes (`[Table]`, `[Column]`, `[PrimaryKey]`, `[Reference]`), and every query is written
against `Supabase.Client`'s fluent Postgrest API (`.From<T>().Where().Filter().Get()`). This
plan replaces that whole stack with Azure SQL Database + EF Core, and is independent of who
issues the JWT (see `azure-auth-analysis.md` for that half).

**Good news discovered while auditing the code**: Row-Level Security was enabled in the initial
schema migration but fully dropped and disabled in a later migration
(`20251008130000_disable_rls.sql`). Every repository already does its own `user_id` filtering in
application code (e.g. `WorkoutPlanRepository.GetWorkoutPlanByIdAsync` filters by both `planId`
and `userId`). That means there's no database-level authorization logic to re-implement — the
existing repository methods are already structured the way an EF Core LINQ rewrite wants them.

**Also good news**: because the WASM migration (see `wasm-migration-plan.md`) moved all data
access behind `WorkoutManager.Api`'s HTTP surface, **the Web project needs zero changes for this
migration.** Everything here is scoped to `WorkoutManager.Data`, `WorkoutManager.BusinessLogic`,
`WorkoutManager.Api`, and the three test projects.

## Target

- **Azure SQL Database, Free offer**: 100,000 vCore-seconds/month + 32 GB storage, free for the
  life of the subscription, up to **10 free databases per subscription** — meaning you can run a
  separate free dev and prod database rather than sharing one.
- **EF Core 9** (`Microsoft.EntityFrameworkCore.SqlServer`) replacing `Supabase`/`Supabase.Postgrest`.
- Repository *interfaces* (`IWorkoutPlanRepository`, `ISessionRepository`, etc.) stay the same —
  only their implementations change. `BusinessLogic` service classes and everything above them
  are untouched.

## Phase 1 — Schema translation

Source of truth is `WorkoutManager.Data/supabase/migrations/`. Table-by-table type mapping:

| Postgres | Azure SQL | Notes |
|---|---|---|
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `bigint IDENTITY(1,1)` | direct equivalent |
| `UUID` | `uniqueidentifier` | direct equivalent |
| `TEXT` | `nvarchar(max)` or `nvarchar(n)` | prefer bounded lengths where the column has an obvious cap (names, notes) |
| `TIMESTAMPTZ` | `datetimeoffset` | preserves UTC offset semantics |
| `BOOLEAN` | `bit` | direct equivalent |
| `SMALLINT` | `smallint` | direct equivalent |
| `DECIMAL(10,2)` | `decimal(10,2)` | unchanged |
| `CHECK (...)` | `CHECK (...)` | SQL Server supports the same constraints, syntax unchanged |
| `REFERENCES auth.users(id)` | **dropped** | `auth.users` is a Supabase-Auth-schema table that won't exist. `user_id` becomes a plain, unconstrained `uniqueidentifier` (or a real FK to a local `Users` table if you go the ASP.NET Core Identity route in the auth doc — decide there first, it affects this) |

One schema cleanup worth doing while you're in here: `plan_day_exercises` has a composite
primary key `(id, training_day_id, exercise_id)`, added specifically per its migration's own
comment to work around a Supabase C# library quirk ("enables proper many-to-many relationship
handling in Supabase C# library"). EF Core doesn't need that workaround — recommend reverting to
a plain `id` primary key plus the existing `UNIQUE (training_day_id, exercise_id)` constraint,
which is the more natural EF Core model and removes Supabase-specific baggage from the schema.

## Phase 2 — EF Core model + DbContext

- Add `Microsoft.EntityFrameworkCore.SqlServer`, `Microsoft.EntityFrameworkCore.Design` to
  `WorkoutManager.Data.csproj`; remove `Supabase` and `Supabase.Postgrest`.
- Rewrite the 8 model classes (`WorkoutPlan.cs`, `TrainingDay.cs`, `PlanDayExercise.cs`,
  `Exercise.cs`, `MuscleGroup.cs`, `Session.cs`, `SessionExercise.cs`, `ExerciseSet.cs`) as plain
  POCOs — drop `BaseModel`, `[Table]`, `[Column]`, `[PrimaryKey]`, `[Reference]`. Configure the
  schema instead via `OnModelCreating` Fluent API in a new `WorkoutManagerDbContext` (keeps the
  models themselves clean and matches how the rest of the codebase already separates concerns).
- Navigation properties (`WorkoutPlan.TrainingDays`, `Session.SessionExercises`, etc.) map
  directly to EF Core `HasMany`/`WithOne` relationships — this is actually a better fit than
  Postgrest's `[Reference]` attribute, which only supported read-side eager loading.
- Generate the initial migration: `dotnet ef migrations add InitialCreate --project WorkoutManager.Data --startup-project WorkoutManager.Api`, review the generated SQL against the table above, apply with `dotnet ef database update`.

## Phase 3 — Repository rewrites

All 7 repositories move from Postgrest fluent calls to EF Core LINQ against
`WorkoutManagerDbContext`. Mechanical for most methods — a few need actual behavioral attention:

- **`SessionRepository.GetSessionHistoryAsync` / `GetActiveSessionAsync` / `GetSessionByIdAsync`**:
  currently fetch sessions, then separately fetch related plans/exercises and stitch them
  together in memory (manual N+1 avoidance, Postgrest doesn't do arbitrary joins well). EF Core's
  `.Include()`/`.ThenInclude()` can replace this with real SQL joins in a single query — a
  genuine simplification, not just a port. Optional, but worth doing while rewriting anyway.
- **`ExerciseRepository.GetLastPerformanceAsync`**: currently filters on a *related* table's
  column via a Postgrest embedded-resource filter string (`.Filter("session_exercises.exercise_id", ...)`).
  This doesn't have a direct EF Core equivalent — needs to become a proper subquery:
  `.Where(s => s.SessionExercises.Any(se => se.ExerciseId == exerciseId))`. Worth a close look
  and a test, since the current Postgrest version of this query is doing something slightly
  unusual (filtering a top-level `Session` query by a nested collection's property) and it's not
  obvious from the code alone that it currently behaves correctly.
- **Pagination** (`SessionRepository.GetSessionHistoryAsync`'s `.Range(from, to)`,
  `WorkoutPlansController`'s page/pageSize pattern): becomes `.Skip((page-1)*pageSize).Take(pageSize)`.
- **`.Filter("id", Operator.In, listOfIds)`** (used in a few places to batch-fetch by ID list):
  becomes `.Where(x => idList.Contains(x.Id))`.

## Phase 4 — Connection string & secrets

- Azure SQL Free tier connection via SQL authentication (username/password) — same shape as
  today's Supabase secret handling: local dev via user-secrets, production via App Service
  Connection Strings configuration (not appsettings.json).
- `WorkoutManager.Api/appsettings.json`'s `SupabaseSettings` section gets replaced with a
  `ConnectionStrings:WorkoutManagerDb` entry (or similar) — same pattern already used for the
  test projects' `ConnectionStrings.DefaultConnection`.

## Phase 5 — Tests

- `WorkoutManager.Api.Tests`, `WorkoutManager.BusinessLogic.Tests`, `WorkoutManager.Data.Tests`
  currently use `Npgsql` + `Respawn` with `DbAdapter.Postgres`. Swap to
  `Microsoft.Data.SqlClient` + `Respawn`'s `DbAdapter.SqlServer` — Respawn supports SQL Server
  natively (it originally targeted SQL Server before adding Postgres support), so this is a
  low-risk swap, not a rewrite of the reset logic itself.
- `TestDataGenerator.cs`, `BaseIntegrationTest.cs`, `IntegrationTestWebAppFactory.cs` need their
  connection setup updated to match.

## Phase 6 — Data migration (decision needed)

Two options, and this is genuinely your call since I don't know how much you value the existing
data:

1. **Fresh start**: stand up the new Azure SQL schema empty, don't port existing rows. Simplest,
   zero risk of data-shape surprises. Reasonable if the current Supabase data is mostly test data.
2. **One-off export/import**: export existing Postgres data (`pg_dump` or a script querying via
   Postgrest), transform, and bulk-insert into Azure SQL. More work, only worth it if there's
   real workout history you want to keep.

## Local development

Free tier gives you up to 10 databases — cheapest option is just using a second free Azure SQL
database for local/dev work, no local install needed. Alternative if you want to work offline:
SQL Server LocalDB (ships with Visual Studio) or a SQL Server Docker container — either works
fine with EF Core, your call based on how often you're offline.

## Effort estimate

| Phase | Description | Est. |
|---|---|---|
| 1 | Schema translation | 1 hr |
| 2 | EF Core model + DbContext + initial migration | 2 hr |
| 3 | Repository rewrites (7 repos, 2 need real behavioral attention) | 4–5 hr |
| 4 | Connection string / secrets wiring | 30 min |
| 5 | Test project swap (Npgsql/Respawn.Postgres → SqlClient/Respawn.SqlServer) | 1.5 hr |
| 6 | Data migration (if chosen) | variable — 1 hr for a fresh start, more for real data export |

**Total: ~9–10 hours** for a fresh start, more if porting real data. Doesn't touch
`WorkoutManager.Web` at all, and is independent of the auth provider choice in
`azure-auth-analysis.md` except for the `user_id` FK decision noted in Phase 1.
